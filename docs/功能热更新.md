# 软件功能热更新协议 v1

Android 1.3.1（基础版本号131）首次加入运行时模块。旧客户端需要先覆盖安装一次本体；之后通过下载签名数据包更新受支持的原生界面及操作逻辑，无需重新安装APK。它与普通任务数据同步、节假日下载、插件APK更新分别独立。

## 客户端

设置 → 版本更新 → 功能热更新，启用开关，选择 GitHub 或已登录的日栖服务端。可手动下载，或开启每12小时系统调度检查。下载校验完成后，下次回到主界面加载；不强行打断当前编辑。没有永久连接或即时推送承诺，后台时机受系统省电策略影响。

GitHub默认地址：`https://github.com/cniv14/DayFlow/releases/latest/download/runtime-update.json`。支持指定签名包地址；未发布时保留基础界面。GitHub不携带云端登录令牌。

服务端固定请求 `GET /v1/runtime-update`，必须携带现有 `Authorization: Bearer <token>`。不需要新注册，使用日栖服务器设置和登录态，不使用TaskFlow令牌。服务器失败、登录过期或超额不会清空用户数据，不会切换到GitHub绕过额度。

设置页固定使用基础APK，可以停用模块并回到基础界面，或回退上一份有效模块。回退保留下载高水位，相同修订不会被自动再次覆盖；要重新发布需要更大修订号。模块加载/渲染异常会停用热更新，运行时未捕获异常后重新打开使用基础版本。仍需设备实测，不保证覆盖系统强杀、所有原生崩溃场景。

## 服务端

服务器只增加上述可选入口；认证、账号隔离、同步v1和CAS格式不变。`server/updates/runtime-update.json`为管理员部署的已签名包，服务器只分发，不持有签名私钥。不要放用户笔记、令牌或私钥在包内。

环境变量：`DAYFLOW_RUNTIME_REQUESTS=10`，`DAYFLOW_RUNTIME_WINDOW_SECONDS=3600`，即每账号每小时最多10次。额度在SQLite独立表持久化，所有设备/会话共享，服务重启不清零；窗口从该账号第一笔请求起计。登录成功后请求入口即计数，包含尚未发布等失败请求，未登录不消耗账号额度。超额返回429及`Retry-After`秒数；原认证限流仍独立生效。404表示尚未部署，401表示需重新登录。每个签名响应最多12MiB。

此包不会从公开的`/updates/`入口提供；该入口继续只提供原APK更新白名单。GitHub模式是单独可选的公开分发渠道，本身不提供账号访问控制。如果希望包只对注册用户开放，请仅部署在服务端，不同时上传GitHub。

## 签名包结构

外层与APK更新签名一致：`{payload: base64(UTF8 JSON), signature: base64(RSA-SHA256签名)}`。使用基础APK内置公钥验证；应用仅接受原发布者签名。服务端管理员不能仅凭登录态签发代码更新。

payload：

```json
{"schema":1,"platform":"android-runtime","api":1,"version":"1.3.1-r1","version_code":1,"min_app_code":131,"max_app_code":131,"entry":"app.dayflow.hotfix.Entry","sha256":"DEX的64位小写SHA256","notes":"说明","dex":"单个classes.dex的base64"}
```

版本号独立于APK，必须递增；`min_app_code`/`max_app_code`必须匹配已安装本体。DEX校验后仅从应用内部存储读取并在内存ClassLoader中加载，不从外部可写路径执行，不安装APK。保留当前包和上一包，内存只缓存一个活动模块。

## 原生模块接口

`app.dayflow.HotModule` ABI 1：`boolean render(android.app.Activity host, String screen, android.widget.LinearLayout container) throws Exception`。屏幕名为`agenda`今天、`note`笔记、`course`日程、`inbox`收集箱；`settings`始终不交给模块。模块用原生Android View创建页面，可调用基础客户端公开能力；返回false继续原页面。不能直接覆盖已加载的基础类，也不能替换未暴露的系统组件。模块不得保留已销毁Activity、退出页面后继续线程或监听。

可更新已接入入口的原生页面、交互和模块业务逻辑；新增权限、Manifest组件、基础ABI、APK资源和未接入模块的底层能力仍需升级主包。当前不是整个Java应用任意方法的透明补丁系统，数据库结构迁移和服务端协议修改也不应通过模块隐式实施。

## 构建发布

原始代码见`examples/hotupdate/Entry.java`，示例替换今天页并复用原生每日清单。示例不会自动启用；发布的`runtime-example.json`可填写到GitHub签名包地址，体验无需重装加载。正式包使用`runtime-update.json`文件名。

```powershell
python tools/build_runtime_example.py --java-home "C:/Program Files/Zulu/zulu-17" --sdk "C:/Users/xingj/AppData/Local/Android/Sdk" --output .tools/runtime-example
python tools/publish_runtime_update.py --dex .tools/runtime-example/dex/classes.dex --key .signing/updates-private.pem --output server/updates/runtime-update.json --version 1.3.1-r1 --code 1 --min-app 131 --max-app 131
```

GitHub：上传签名JSON至Release附件。服务端：原子替换挂载目录内的`runtime-update.json`，不需重启或重新安装客户端。签名工具不会上传私钥。服务端安装包附带签名工具与模块示例源码；签名步骤在维护者机器执行（Python构建工具需要cryptography，服务端运行本身无需额外依赖）。

动态代码加载遵循Android官方安全建议，仅加载可信签名代码。内存加载不生成外部可写DEX文件。参考[官方安全说明](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)和[Android 14动态加载约束](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading)。
